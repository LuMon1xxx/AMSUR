# АМСУР — план проекта для пользователя

## 1. Идея проекта

**АМСУР (Автоматический модуль составления учебных расписаний)** — настольная программа для автоматического составления школьного расписания.

Главная задача программы — не просто составить любое расписание, а **найти максимально хорошее расписание школы по заданным пользователем правилам**.

Пользователь вводит данные школы один раз или обновляет их при необходимости:
- классы и их смены;
- предметы;
- учителей и предметы, которые они могут вести;
- закреплённых за классами учителей по каждому предмету;
- кабинеты и их оснащение;
- учебную нагрузку;
- подгруппы;
- дни и количество уроков;
- при необходимости дополнительные правила и пожелания.

После этого пользователь выбирает профиль качества и запускает генерацию.

## 2. Главный принцип генерации

Программа работает не по принципу «нашла первое расписание и остановилась».

Она должна:
1. найти допустимое расписание;
2. сохранить его как лучшее найденное;
3. продолжать поиск;
4. когда найдено лучшее расписание — заменить лучший результат;
5. поддерживать список **Top-5 лучших существенно отличающихся вариантов**;
6. продолжать поиск до остановки пользователем или до заданного лимита.

При остановке всегда сохраняется лучшее найденное расписание.

Важно: результат должен называться **«лучшее найденное»**, если математически не доказана абсолютная оптимальность.

## 3. Что именно должна оптимизировать программа

Главный приоритет — **не допустить конфликтов и получить максимально удобное расписание**.

### Обязательные ограничения

По умолчанию нельзя:
- поставить одному классу два урока одновременно;
- поставить одному учителю два урока одновременно;
- использовать кабинет несовместимым образом;
- одновременно использовать один и тот же ресурс там, где это запрещено;
- нарушить смену класса;
- нарушить синхронность обязательных подгрупп;
- назначить закреплённому за классом предмету другого учителя без явной настройки пользователя.

### Сильно нежелательные нарушения

Некоторые условия не должны делать задачу автоматически невозможной. Если выполнить их невозможно, программа должна допустить нарушение и дать большой штраф.

Например:
- специализированный кабинет недоступен, но предмет проведён в другом допустимом кабинете;
- одно окно у учителя;
- слишком большая дневная нагрузка;
- неидеальное распределение предметов.

### Мягкие пожелания

Программа стремится минимизировать:
- окна учителей;
- неудобное распределение предметов;
- слишком большое количество уроков в один день;
- плохие сочетания предметов;
- нежелательные кабинеты;
- переходы между удалёнными кабинетами;
- другие пользовательские пожелания.

## 4. Окна

Для учеников окно должно быть **практически недопустимым по умолчанию**: программа должна стремиться к нулю окон.

Но окно ученика не должно автоматически ломать всё расписание, если идеальный вариант невозможен. В таком случае оно получает очень большой штраф.

Для учителей окна также плохи, но штраф должен быть существенно меньше, чем за окно ученика.

Таким образом программа сначала пытается получить:
**0 окон у учеников → минимум окон у учителей.**

## 5. Профили генерации

Перед генерацией пользователь сможет выбрать готовый профиль.

Предлагаемые профили:

### Стандартный
Для обычной школы. Баланс между главными критериями.

### Для учеников
Особенно сильный приоритет отсутствия окон и удобного распределения уроков учащихся.

### Для учителей
Более сильное внимание к окнам, нагрузке и удобству рабочего дня учителей.

### Нормативный
Повышенный приоритет соблюдения нормативных требований.

### Пользовательский
Пользователь сам регулирует веса основных критериев.

Профили не должны позволять отключить критические физические ограничения.

## 6. Настройка штрафов

Пользователь сможет менять веса правил без изменения кода.

При этом обычный пользователь увидит простые названия:
- «Окна у учеников»;
- «Окна у учителей»;
- «Соблюдение норм»;
- «Предпочтительный кабинет»;
- «Количество уроков в день»;
- «Распределение предметов» и т. п.

Продвинутые пользователи смогут открыть расширенные настройки.

## 7. Предметы

В программе должен быть встроенный справочник типовых предметов белорусской школы.

Но этот справочник должен быть **версионируемым**, а пользователь должен иметь возможность:
- добавить свой предмет;
- изменить название;
- отключить ненужный предмет;
- изменить доступность предмета для конкретных классов.

Точный состав встроенного набора перед релизом должен быть сверён с актуальными официальными учебными планами и программами Республики Беларусь, а не просто считаться «вечным» списком.

## 8. Учителя

Для каждого учителя должны задаваться:
- имя;
- предметы, которые он может преподавать;
- дополнительные ограничения доступности;
- при необходимости предпочтения.

Ключевое правило: **за каждым классом и предметом закрепляется основной учитель**.

Например:
> 10Б → математика → Иванов.

Все уроки математики 10Б в сгенерированном расписании по умолчанию ведёт Иванов.

Система замен может существовать отдельно, но не должна менять основной принцип.

## 9. Кабинеты

Каждый кабинет можно визуально настроить.

Минимально:
- название;
- этаж/здание при необходимости;
- специализация;
- допустимые предметы;
- дополнительные характеристики.

Большинство кабинетов по умолчанию считаются универсальными.

Специализированные кабинеты могут получать большой штраф при замене на универсальный, а физкультура — отдельные ограничения.

Пример:
> Кабинет 205 — информатика.
> Кабинет 206 — химия.
> Кабинет 101 — универсальный.

Интерфейс настройки должен быть графическим: дерево/структура школы, этажи, кабинеты и быстрый переход между ними.

## 10. Подгруппы

Поддерживаются подгруппы.

Пример:
> 8А → английский → группа 1 + группа 2.

Каждая подгруппа может иметь своего учителя и кабинет.

По умолчанию — две подгруппы. При необходимости пользователь сможет создать больше.

Подгруппы должны корректно работать даже при разных способах деления по разным предметам.

## 11. Дни и уроки

По умолчанию используется пятидневная неделя.

Допускается шестой день.

Номер урока важнее точных часов на первой версии:
> 1 урок, 2 урок, ... 8 урок и т. д.

При необходимости пользователь сможет задать точное время звонков.

Смена задаётся отдельно для каждого класса.

## 12. Распределение нагрузки

Пользователь указывает, например:
> 7А → математика → 5 часов в неделю → Иванов.

Программа должна обеспечить выполнение этой нагрузки.

Можно настраивать:
- сколько раз предмет может стоять за день;
- желаемое число дней предмета;
- дополнительные связи между предметами.

Например:
> математика — максимум 1 раз в день;
> русский + литература — желательно в один день.

## 13. Сложность предметов

Каждому предмету можно назначить сложность.

Также должна существовать возможность переопределить её конкретно для класса.

Пример:
> Математика = 5/5.
> Для 10Б математика = 4/5.

Сложность используется как фактор качества и в нормативных правилах, а не как жёсткое абсолютное свойство.

## 14. Классный руководитель и общие события

Для класса можно задать классного руководителя.

Можно создавать специальные события, например:
> Классный час → четверг → 1 урок.

Если правило обязательно — оно становится жёстким.
Если желательно — используется штраф.

## 15. Top-5

Программа должна показывать пять лучших существенно различных вариантов.

Пример:

| Место | Итоговый штраф | Описание |
|---|---:|---|
| 1 | 18 | лучший общий баланс |
| 2 | 21 | меньше окон учителей |
| 3 | 23 | лучше распределены кабинеты |
| 4 | 26 | другое распределение предметов |
| 5 | 29 | альтернативный вариант |

Почти одинаковые варианты не должны бессмысленно вытеснять разнообразные решения.

## 16. Объяснение качества

Для каждого варианта показывается не только общий балл, но и состав результата.

Пример:

> **Штраф: 18**
> - окна учеников: 0;
> - окна учителей: +6;
> - кабинеты: +4;
> - распределение предметов: +3;
> - предпочтения: +5.

Также должна быть видна причина, почему один вариант лучше другого.

## 17. График поиска

Во время генерации желательно показывать:
- время поиска;
- найдено решений;
- текущий лучший штраф;
- обновления Top-5;
- простой график улучшения результата.

Например:
> 70 → 51 → 38 → 25 → 19 → 18.

Это одновременно полезно пользователю и очень хорошо для демонстрации проекта на конкурсе.

## 18. Ручная корректировка

Пользователь может менять готовое расписание мышью.

При перемещении программа заранее показывает:

**✓ Можно** — всё допустимо.

**⚠ Можно, но качество ухудшится** — например +2 штрафа.

**⛔ Нельзя** — с понятной причиной.

Пример:
> ⛔ Учитель Иванов уже проводит урок у 7Б в это время.

После изменения общий рейтинг пересчитывается автоматически.

Будут Undo/Redo.

Также желательна функция:
> **Исправить автоматически** — программа пытается переставить небольшое количество уроков, чтобы выполнить желание пользователя.

При этом автоматическое изменение всего школьного расписания ради одной ручной правки не должно происходить без согласия пользователя.

## 19. Диагностика невозможности

Если расписание составить невозможно, программа не должна показывать просто:
> «Ошибка».

Она должна анализировать ситуацию и объяснять вероятные причины.

Например:
> «Для 8А требуется 5 часов химии, но специализированный кабинет доступен только 4 урока».

И предлагать возможные действия:
- изменить доступность кабинета;
- разрешить другой кабинет;
- изменить нагрузку;
- изменить учителя;
- изменить правило.

Важно честно различать:
> «математически доказано, что в текущей модели решения нет»
и
> «алгоритм не нашёл решение за отведённое время».

## 20. Замены

Система замены не является главным компонентом V1.

Если она реализуется, она должна позволять задать:
> Основной учитель → допустимые заменяющие учителя.

Приоритет отдаётся учителю той же специальности/предметной области.

Но замена не должна автоматически перестраивать всё школьное расписание.

## 21. Сохранение

Нужно сохранять:
- школу;
- данные;
- настройки;
- результаты генерации;
- выбранное расписание.

Желательно сохранять варианты Top-5 и историю изменений.

## 22. Экспорт

Минимум:
- Excel;
- PDF.

Отдельные представления:
- по классам;
- по учителям;
- по кабинетам.

Главный формат для школы — расписание классов.

## 23. Настройка интерфейса

Главный принцип:

> **простота для обычного пользователя + глубокие настройки для продвинутого пользователя.**

Обычный путь:
> Данные → Профиль → Сгенерировать → Выбрать → Проверить → Печать.

Дополнительные настройки должны раскрываться постепенно.

## 25. Что особенно важно для конкурса

Главный научно-технический тезис:

> АМСУР представляет школьное расписание как задачу дискретной оптимизации с большим количеством ограничений и предпочтений и выполняет длительный поиск всё более качественных допустимых решений.

Самыми сильными демонстрационными функциями должны быть:
1. ввод реальной школы;
2. нажатие «Сгенерировать»;
3. первое найденное расписание;
4. постепенное улучшение;
5. Top-5;
6. объяснение штрафов;
7. ручная коррекция с мгновенной проверкой;
8. экспорт готового расписания.

## 26. Критерий успеха

Проект успешен, если обычный пользователь без знания программирования способен:

> внести данные школы → нажать генерацию → получить допустимое расписание → увидеть несколько лучших вариантов → выбрать один → немного поправить его вручную → получить корректное расписание для использования школой.

При этом алгоритм должен стремиться быть **быстрее ручного составления и выдавать более качественный результат**.

## 27. Что не должно отвлекать от главной цели

В первую очередь нельзя жертвовать качеством solver ради:
- красивой второстепенной функции;
- сложной многопользовательской системы;
- веб-версии;
- мобильного приложения;
- чрезмерно сложной диагностики.

Главный объект проекта — **алгоритм составления хорошего расписания**.
