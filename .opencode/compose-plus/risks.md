# RISKS — остаточные риски редизайна (только UI)

- **R1 Выдуманные цифры просочатся в UI.** Триггер: в XAML появляется число без binding к контракту (%, итерации, память). Митигация: ревью каждого пакета grep'ом чисел; правило «нет binding — нет цифры».
- **R2 Мёртвая кнопка (masking).** Триггер: кликабельный контрол без хендлера/контракта. Митигация: каждая кнопка в пакете маппится на таблицу plan.md; disabled только с бейджем «Скоро» (PDF).
- **R3 Регресс STA/E2E.** Триггер: переименование x:Name/x:FieldModifier, ломающее WpfShellTests/WorkingVersionFlowTests. Митигация: имена контролов не переименовывать, только стили/композицию; полный тест после каждого пакета.
- **R4 Потеря доступности Generate (F5/EXPERT).** Триггер: EXPERT не открывает Settings, CTA не запускает генерацию без данных. Митигация: сохранить хендлеры OnGenerate/OnModeChecked, CTA disabled без HasData.
- **R5 Кабинет-фильтр как scope-creep.** Триггер: фильтр требует изменения store/problem. Митигация: только _allRows.Where(r.RoomName==name); если Rooms пусты («—») — фильтр показывает пусто честно, без новых сущностей.
- **R6 Preview-вердикты в 3 стиля.** Триггер: парсинг VerdictText ломается на новых формулировках. Митигация: стилизация по префиксу мягкая (fallback — нейтральный стиль), текст не перефразируем.
- **R7 Скриншот-цикл без конца.** Триггер: пиксельная гонка со Stitch. Митигация: max 2–3 раунда vision на окно; дальше — backlog, окно считается готовым при отсутствии confirmed CRITICAL/HIGH.

# Остаточные риски после пакета фиксов движка/тестов (16.10.2026)

## 1. OrTools-модель без дневного максимума класса — ЗАМЕРЕНО: не причина отказов
`OrToolsSolver` содержит только teacher MaxPerDay (`OrToolsSolver.cs:540`);
ограничения «не более MaxLessonsPerDay занятий класса в день» в CP-SAT-модели нет,
хотя `PlacementValidator:233` считает его Hard. В soft-термах его тоже нет: код
`class-maxperday` в каталоге с весом 0 и в `SoftEvaluator` не начисляется, так что
градиента к его соблюдению у поиска нет — только гейт валидатора.

Замер 16.10.2026 (временный зонд на карантинной tight-фикстуре `MidSchoolTightTests`,
994 occ, бюджет 12 с, seed 11, presolveA=false; зонд откачен):
```
status=Unknown hard=0 place=0/994 firstMs=0 wallMs=5633
Greedy: placed 989/994 in 228ms, starts 4 (hints for phase A)
Greedy unplaced: 6А|Информатика|Савицкая А.В.; 6Г|Иностранный язык|Лебедева А.В.;
                 6В|Русский язык|Новикова А.В.; 10Б|Информатика|Савицкая А.В. (A+B)
No solution within limit (timeout ≠ infeasible).
```
Строки `VALIDATOR REJECTED` в диагностике НЕТ → отказ приходит не от валидатора, а
раньше: `resA.Values is null` (`OrToolsSolver.cs:184-192`), то есть модель CP-SAT не
нашла решения вообще (и не доказала неразрешимость). Значит отсутствие капа класса в
модели — НЕ причина наблюдаемого «solver Unknown/place=0». Причина — 5 занятий,
которые не разместил уже greedy (пулы Савицкая/Лебедева/Новикова); это ровно тот
список кандидатов, что указан в карантинной пометке автора
(`MidSchoolTightTests.cs:537-540`).

Вывод: hard-ограничение капа класса само по себе карантинную фикстуру не чинит, и
добавлять его без замеров не обосновано (ср. пометку автора «не вслепую»).
Отдельно к профилированию фаз: фаза A вернула Unknown за 5.6 с при бюджете 12 с —
это задача про бюджет/пресет фаз, не про модель.

Остаточный риск (теоретический, не наблюдался): модель может выдать incumbent с
перегрузом класса по дню, который `Accept` отвергнет; на всех покрытых фикстурах
прогоны дают Hard==0 и place>0.
Триггер пересмотра: появление `VALIDATOR REJECTED` с кодом `class-maxperday` в
диагностике генерации.

## 2. ChainLns: минимум 1 с на стадию × 16 стадий
`ChainLns.Improve` фактически не ограничен `budget` снизу: `stageBudget` не меньше
1 с, стадий 4×4=16 → до ~16 с при любом бюджете.
Путь вызывается только из тестов (`ChainLnsTests`, бюджет 20 с), в прод-конвейер
не подключён, поэтому реального влияния нет.
Правка изменит поведение тестов сходимости без пользы.

## 3. IncrementalEvaluator не учитывает RelaxedStrict
Ослабленные пользователем строгие коды (`student-gap`, `student-late-start`,
`class-maxperday`, `teacher-maxperday`) в DnD-превью остаются Forbidden, тогда как
`PlacementValidator` переводит их в Warnings.
Оставлено сознательно: тесты держат инвариант «разрешённое редактором разрешено и
движком» (`TeacherGapSplitTests`, `DoublesAdjacencyTests`, `ActiveDayTests`), а
`SearchIndex`/`LocalSearch` relax не учитывают. Ослабление только в одном месте
ломает паритет (редактор стал бы мягче движка).
Плюс production-путь `ManualEditService:27` вызывает `Evaluate` без rules — то есть
с дефолтным набором, где ослаблений нет.
Триггер: если в UI включат ослабление строгих и пользователь упрётся в «нельзя
переставить». Тогда relax надо проводить сразу в Validator + SearchIndex +
IncrementalEvaluator.

## 4. Метрика CandidateArchive.RejectedWorseCount не отражает ничего (ветка недостижима)
В ветке «кандидат не лучше худшего» счётчики `RejectedWorseCount` и
`RejectedSimilarCount` инкрементируются вместе, хотя фактическая причина —
похожесть (строго лучше отсортировано выше). Поведение приёмки при этом корректно.
Уточнение 16.10.2026: ветки «отвергнут как хуже» в архиве нет вообще — кандидат,
который не лучше и не похож, принимается ради разнообразия. То есть корректная
правка — не «инкрементировать один счётчик», а удалить метрику целиком; это
изменение публичного API + правка тестов-принтов ради нуля функциональной пользы.
Оставлено сознательно.
Триггер: если метрика начнёт влиять на решения алгоритма.

## 8. Строгие гейты vs ослабленные профили: проверено — это замысел, не баг
Дефолтным (строгим) набором правил валидируют: `OrToolsSolver.Accept:411`,
`AcceptScheduleService:18`, `ManualEditService:62`, `GenerationOrchestrator:180`,
`ScheduleCsvExporter:19`, `ScheduleHtmlExporter:20`, `ScheduleExcelExporter:40,302`.
При этом `GenerateHost.cs:27` передаёт в солвер профиль пользователя (`rules: rs`), и
`rs` идёт в soft-веса, в LS (`OrToolsSolver.cs:216`) и в ослабленный экспорт черновика
(`ScheduleExcelExporter:179`). Выглядит как разъезд, но проверено, что это конвенция:
«принять и сохранить можно только strict-clean» (INV-01). Фичи, которым нужно
«разрешить перегрузку», меняют не гейт, а саму задачу — `ProblemBuilder:449-471`
поднимает учителю `MaxLessonsPerDay` (D-39), после чего строгий валидатор проходит.

Следствие (осознанное ограничение продукта): подтверждённое пользователем ослабление
строгого кода (B2) не приводит к принятию расписания с этим нарушением — нарушение
видно как warning в ослабленном черновике-экспорте, а генерация остаётся strict.
Триггер пересмотра: если продукт потребует «сгенерировать и принять расписание с
подтверждённым нарушением» — тогда `rules` надо провести во ВСЕ гейты сразу (солвер +
AcceptScheduleService + GenerationOrchestrator + экспортёры + ManualEditService),
иначе сломается паритет «редактор мягче движка».
